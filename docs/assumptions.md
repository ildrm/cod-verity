# Assumptions and conservative decisions

* New automation defaults off so installation does not begin sending mail before configuration. Auto-expiry cancellation defaults off.
* The native COD status filter is the primary gateway boundary for both Classic and Block paths. Fresh admin-created pending → on-hold orders are also considered; other historical/manual orders require explicit enrollment. Existing-order checks use current policy with the global enable flag bypassed only for an explicit staff start.
* Pending payment, held and processing orders may be evaluated for eligibility. Explicit manual start is limited to held/processing orders, since pending payment may not have completed checkout. Staff must confirm an existing processing order has not shipped before deliberately holding it.
* Customer cancellation requires an unchanged on-hold COD order with no paid timestamp. Only plugin-owned processing → on-hold holds can be released automatically. Unknown/custom statuses, completed/refunded/cancelled orders and conflicting edits are not forcefully changed.
* Fulfillment integrations must respect WooCommerce order status. No generic plugin can discover unrecorded shipments or control integrations that ship on order creation regardless of a hold. Arbitrary third-party direct SQL bypasses WooCommerce hooks and is outside serialization. Test actual warehouse/shipping integrations in staging.
* Database named locks are required and assumed connection-stable. MySQL/MariaDB proxy configurations that multiplex a request across server connections are unsupported. A missing lock/persistence facility prevents unsafe enrollment and surfaces an operational error. Normal WooCommerce CRUD saves participate in the order lock; connection death releases it.
* Mail cannot be atomically committed with a database write. Ambiguous worker crashes produce a visible unknown outcome and require explicit reissue; automatically retrying an uncertain send risks duplicate mail. Configured transport failures use bounded retries.
* Monetary boundaries use exact decimal strings, not binary floating point. Thresholds use store precision; mixed-currency extensions need independent staging validation because no conversion service is included.
* Product-category IDs are exact matches, including variation parent categories. Descendant expansion is not implicit. Category selection displays a bounded 500 terms.
* Phone normalization only strips nondigits; no international-equivalence guarantee. Duplicate detection compares enrolled requests in the lookback and is always advisory. Matches are capped at 20.
* Reissue/stop do not permit unsafe order-state bypass. Requests interrupted by content/status changes cannot be reissued unless the original guard is restored deliberately; staff may instead manage the order outside verification. Confirmed/cancelled requests cannot be reset.
* Reports use original request creation dates and current outcomes. Customer timing begins at latest generation issue and excludes staff responses. Reissues do not inflate requests initiated. Optional time-saved estimates are omitted to avoid unsupported business claims.
* UTC epoch storage is used everywhere; site-local dates are display/filter inputs. Retention is eventual, bounded and cron-dependent. Minimal enrollment tombstones remain until deliberate erasure/uninstall.
* Multisite network activation is rejected; activate per site. Deactivation cannot infer whether staff should release held orders, so it preserves statuses and warns in documentation. Reactivation resumes reconciliation.
* The plugin version is 1.0.0. Release readiness is a verification conclusion, not implied by the version number or packaging. No tested-up-to version is advertised without the corresponding recorded execution.
